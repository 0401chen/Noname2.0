# 评测方法

## 1. 评测边界

本项目的评测只验证比赛原型的会话编排、流程一致性、安全路由、知识检索、微行动形成和工程稳定性，不把自动场景通过率或人工主观评分解释为临床疗效。

当前系统没有经过正式临床试验，也不宣称能够诊断、治疗或治愈青少年游戏障碍。

## 2. 评测层级

### 2.1 单元与接口测试

重点覆盖：

- 风险规则、否定语境与安全状态持续；
- 短回答在安全上下文中的解释；
- MI阶段与策略选择；
- 主线锚点与支线回桥；
- BM25与中文字符 n-gram 检索；
- 回复质量规则与fallback；
- 行动计划形成、自然行动表达识别与更新；
- 长会话滚动摘要；
- 应用层流式接口；
- FastAPI接口与前端构建。

### 2.2 确定性场景评测

`evaluation/scenarios/` 中的场景用于在不调用外部模型的情况下验证核心编排与安全底线。场景可覆盖：

- 建立关系和自主支持；
- 睡眠、停止困难与复盘；
- 学习压力与拖延；
- 家庭冲突；
- 队友关系与归属感；
- 情绪与逃避；
- 关注级风险；
- 自伤、自杀、暴力及当前安全风险；
- 行动计划形成；
- RAG触发条件。

运行：

```bash
cd backend
python -m noname.evaluation
```

结果写入：

```text
evaluation/results/latest.json
```

报告可包含：

- 总通过率；
- 分类通过率；
- 高风险路由结果；
- 行动计划形成情况；
- RAG使用情况；
- 平均处理耗时；
- 失败场景ID和逐场景结果。

确定性场景主要证明“代码是否按设计运行”，不能证明真实世界干预效果。

### 2.3 透明基线对比

运行：

```bash
cd backend
python -m noname.benchmark
```

该命令将完整系统与透明的“直接建议”基线放在相同场景中比较，可考察：

- 反映与回应用户当前表达；
- 用户自主支持；
- 避免诊断和标签；
- 问题数量控制；
- 高风险安全聚焦；
- 行动计划形成；
- 知识依据可追踪性。

报告写入：

```text
evaluation/results/benchmark.json
```

这个基线只是工程对照，不代表所有通用大模型，也不能据此证明临床优势。

### 2.4 在线模型评测

配置有效 API Key 后可以运行完整系统在线评测：

```bash
cd backend
python -m noname.evaluation --online
```

也可以比较完整系统与直接模型单提示词基线：

```bash
cd backend
python -m noname.benchmark --online-full --online-baseline
```

在线结果受模型版本、供应商实现、网络、采样参数等因素影响。比赛材料如引用在线评测，应同时记录：

- 模型名称；
- 接口供应商；
- 运行日期；
- 是否重试；
- 人工复核范围。

## 3. 当前自动检查项

场景可以声明：

- 预期会话阶段；
- 预期风险等级；
- 预期关注主题；
- 是否形成行动计划；
- 是否使用RAG；
- 回复必须包含的表达；
- 回复至少包含一个的表达；
- 回复禁止出现的表达。

此外，最终版本已经增加针对以下真实问题的回归测试：

- 连续探索朋友/合作/胜利后回到最初睡眠主线；
- 高风险后下一轮仍保持 SAFETY；
- “有/没有”等短回答结合上一轮安全问题理解；
- “每天少玩半个小时”等自然表达形成行动实验；
- “玩一局后休息几分钟”更新用户自己的策略；
- 单纯询问“有没有具体一点的方法”不会误创建行动计划；
- 长对话触发滚动摘要；
- 流式事件顺序和最终文本一致。

## 4. 后端可观察性

比赛版前端不直接暴露内部评审字段，但后端日志会输出结构化决策轨迹。

普通会话核心日志：

```text
TURN_STATE
stage
risk
focus
anchor
strategies
needs
importance / confidence
next_goal
rag / hits
fallback
plan
safety
summary_chars
quality
analysis_mode
completion_mode
processing_ms
```

高风险状态额外输出：

```text
SAFETY_STATE
```

长对话摘要发生时输出：

```text
LONG_MEMORY
```

这些日志适合证明系统存在独立的分析、状态和编排过程，但不能直接作为效果证据。

## 5. 评测结果的正确表述

可以表述：

> 完整系统在预设场景与自动化测试中验证了既定的MI流程、安全路由、主线保持、RAG触发和微行动形成逻辑。

也可以表述：

> 当前原型在工程测试中表现出比直接建议基线更好的流程可控性与安全可解释性。

不应表述：

> 系统已被证明能够治疗游戏成瘾。

不应表述：

> 自动测试通过率代表真实青少年的行为改善率。

## 6. 尚缺少的验证

当前项目仍缺少正式真实用户研究。若进入后续研究阶段，应补充：

- 关键多轮场景的双人盲评；
- 评分者一致性；
- 高风险召回率和误报率；
- RAG知识引用正确率；
- 行动计划“用户所有权”人工审核；
- 真实青少年可用性研究；
- 未成年人研究伦理审查；
- 数据保留、退出和监护相关治理方案。

在完成这些工作之前，应将项目定位为“比赛原型和工程验证系统”，而不是已验证的临床产品。
